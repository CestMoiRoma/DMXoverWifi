# Troubleshooting

[Wiki index](../../WIKI.md)

Failures that have actually happened, and what each one meant.

## The rig

**A fixture responds on the wrong address.**
The address is `start_channel + offset - 1`. A fixture starting at 10 with a
channel at offset 1 drives address 10, not 11.

**A fixture does not respond at all, and the wiring looks right.**
Swap DMX pins 2 and 3. Minus is pin 2 and plus is pin 3, and getting them the
wrong way round damages nothing and does nothing. After that, suspect the
personality the fixture is in: manuals disagree with hardware more often than you
would expect. Probe raw addresses one at a time from the serial console with
`Set-Value address=<n> value=255` and write down what actually lights up.

**A long chain behaves differently depending on what is plugged in.**
Fit the 120 ohm terminator at the far end. Reflections on an unterminated line
look exactly like an intermittent firmware fault.

**A pin change had no effect.**
`tx-pin` and `dir-pin` are read once, at startup. Reboot.

**A DMX pin setting is ignored on the ESP8266.**
Expected. The output there is fixed to `Serial1` on GPIO 2. The direction pin
still works.

## Getting to it

**Cannot reach the UI.**
Check `get-status wifi` over serial. `mode=ap` means it fell back to its hotspot,
so join `ESP-DMX` and browse to <http://1.1.1.1>.

**`esp-dmx.local` does not resolve.**
mDNS is not universal. Use the address the router gave it, which
`get-status wifi` prints.

**The serial port opens but nothing answers.**
The console is silent by design: no banner, no prompt, no boot log, and it only
ever replies to a command. Send `Help` and press Enter before concluding it is
dead. Beyond that: the board's own USB serial device rather than a Bluetooth COM
port, 115200 baud, and a terminal that asserts DTR on the ESP32-S2's native USB
port. `pio device monitor` does.

The port number follows the firmware on the ESP32-S2, because the USB PID changes
with it. A board that was on one COM port under a different firmware comes back
on another.

**Opening the port fails with "access denied" or `PermissionError(13)`.**
Something else holds it, and COM ports are exclusive. Usually a monitor left
running in another terminal, or an editor extension that reopens the port by
itself, which is invisible in a process list because it runs inside the editor.
Stop every monitor, then unplug and replug. The same clash makes `upload` and
`uploadfs` fail.

## MQTT

**Nothing appears in Home Assistant.**
Read the status line under **Settings**, **API**. It names the reason. The
[MQTT page](mqtt.md) lists what each one means.

**It says connected, but entities are missing.**
The detail line counts what was published. If the count is lower than your
channel count, the broker is refusing large retained payloads or the discovery
prefix does not match the one Home Assistant listens on.

**Entities exist for a fixture that was deleted.**
That should no longer happen: deleting a fixture withdraws its discovery. An
entity left from an older firmware is cleared by publishing an empty retained
payload to its config topic, or by removing it in Home Assistant.

**A `.local` broker name does not work on the ESP8266.**
Its mDNS responder can answer questions but not ask them. Use an address.

## Updates

**The board refuses the file.**
The name mentioning `littlefs` or `spiffs`, or a first byte that is not `0xE9`,
means it is not a firmware image. Take `firmware.bin` from
`.pio/build/<environment>/`.

**The upload stops partway.**
Nothing was installed: the partitions only switch after the whole image is
written and verified. Reload and try again.

**Check GitHub says it could not reach GitHub.**
The **browser** fetches the release, not the board, so this is your laptop's
internet connection rather than the board's. A repository with no releases yet
says so separately.

## The build

**The build pulls the wrong DMX backend, or a link error mentions `Serial1`.**
Each backend is guarded by an ESP8266 or ESP32 macro and PlatformIO picks the
toolchain from the environment. Build with an explicit one, `pio run -e s2mini`,
rather than mixing artifacts.

**A build of several environments at once failed, then passed unchanged.**
That was `src/web_assets.cpp` being regenerated by one environment while another
compiled it. Fixed by writing it through a temporary file; if you see it again in
another generated file, that is the shape of the bug.

**The UI is blank or 404s but the API works.**
It is not a `uploadfs` problem any more: the page lives in the firmware. A
headless build (`WITH_WEBUI=0`) drops the page routes on purpose and keeps the
API. Check which environment was flashed.

**`/style.css` and `/app.js` return 404.**
Correct. Those files are not on the board at all: `tools/pack_web.py` splices
them into the page at build time so a load is a single request with nothing left
to race. Edit them in `web/` as usual and rebuild.

## Performance

**A cue arrived late, or a fader felt sluggish.**
Expected. See [Timing and latency](timing.md). There are no delivery or timing
guarantees.

**The UI is unresponsive and connections are being reset.**
Something is blocking the main loop. `/api/info` reports `loop_max_us`; a healthy
board is under 5 ms and a blocked one is in the seconds. The timing page lists
the three that have caused this before and what they had in common.
